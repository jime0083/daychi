## P-001: Firestore Emulatorに必要なJava実行環境がPATHに存在しない
- 記録日: 2026-09-19
- 状態: 解決済み
- 発生箇所: タスク1-3(Firebase Emulator Suite設定)
- 問題内容:
  想定した動き: java -version が通り、Firestore Emulator(JRE依存)が起動できる
  実際の動き: 「Unable to locate a Java Runtime.」でjavaコマンドが失敗し、Emulatorが起動できない
- 再現手順:
  1. ターミナルで java -version を実行 → エラー
- 原因調査:
  - /usr/libexec/java_home も失敗し、システム標準のJavaランタイムは未インストール
  - Homebrewでは /opt/homebrew/opt/openjdk (openjdk 26.0.1) がインストール済みで、
    直接パス指定での動作確認は成功(/opt/homebrew/opt/openjdk/libexec/openjdk.jdk/Contents/Home/bin/java)
  - ただし brew link されておらず /opt/homebrew/bin に露出していないためPATHから解決できない
- 特定した原因:
  Homebrew版openjdkがインストール済みだが未リンク(keg-only)のため、javaコマンドがPATH上に存在しない
- 切り出したタスク: manual-work.txt Work 9(Java実行環境のPATH設定)
- 解決日: 2026-09-19
- 解決内容:
  ユーザー承認のうえ brew link --force --overwrite openjdk を実行(37 symlinks created)。
  java -version で openjdk 26.0.1 が返ることを確認。状態を「解決済み」とする

## P-002: クリーンな状態で npx tsc --noEmit が LayoutProps 未定義エラーで失敗する
- 記録日: 2026-09-19
- 状態: 解決済み
- 発生箇所: src/app/layout.tsx:20(タスク1-3実装中に発覚。1-3の変更とは無関係)
- 問題内容:
  想定した動き: 完了前必須チェックの npx tsc --noEmit がいつでもパスする
  実際の動き: .next ディレクトリが無い状態では
  「src/app/layout.tsx(20,50): error TS2304: Cannot find name 'LayoutProps'.」で失敗する
- 再現手順:
  1. .next ディレクトリを削除(またはクリーンな状態でclone)
  2. npx tsc --noEmit を実行 → TS2304エラー
- 原因調査:
  - layout.tsx:20 は create-next-app(Next.js 16)標準テンプレートのまま LayoutProps<"/"> を使用
  - LayoutProps は Next.js 16 が next dev / next build / next typegen 実行時に
    .next/types へ自動生成するグローバル型(tsconfigのincludeで取り込まれる)
  - 現在 .next が存在しないことを確認し、エラーを再現
  - タスク1-1/1-2の検証時は devサーバー起動後(.next生成済み)だったため偶然パスしていた
- 特定した原因:
  自動生成型 LayoutProps に依存するコードに対し、型生成(next typegen)を伴わない
  素の tsc --noEmit を実行していたため。チェックコマンド側の手順不足が根本原因
- 切り出したタスク: progress.txt タスク1-7(型チェックコマンドの安定化)
- 解決日: 2026-09-19
- 解決内容:
  npm script "typecheck"(next typegen && tsc --noEmit)を追加(コミット c863078)。
  .next 削除済みのクリーン状態から npm run typecheck が2回連続でパスすることを
  実装・レビュー双方で確認。以後の型チェックは npm run typecheck に統一
  (CLAUDE.mdのコマンド表も更新済み)

## P-004: npm run lint が e2e/artifacts の生成物を走査して大量エラーになる
- 記録日: 2026-09-22
- 状態: 解決済み
- 発生箇所: eslint.config.mjs(タスク2-1の検証中に発覚)
- 問題内容:
  想定した動き: npm run lint がプロジェクトのソースのみを対象にパスする
  実際の動き: npm run e2e 実行後、e2e/artifacts/html-report 配下のPlaywright生成JS
  (圧縮済み)をESLintが走査し、259エラー・約2795警告で失敗する
- 再現手順:
  1. npm run e2e を1回実行(e2e/artifacts/html-report が生成される)
  2. npm run lint を実行 → 生成物由来の大量エラーで失敗
- 原因調査:
  - eslint.config.mjs の globalIgnores は .next/**, out/**, build/**, next-env.d.ts のみ
    を除外しており、e2e/artifacts/** が除外対象に入っていない
  - ESLint(flat config)は .gitignore を自動参照しないため、gitignore済みでも走査される
  - npx eslint src e2e --ignore-pattern 'e2e/artifacts/**' は exit 0(2-1コード自体は健全)
    → 失敗はすべて生成物由来と確認
  - 1-6のレビューでlintがパスしたのは、lint実行時点でartifactsが未生成だった等の
    実行順序に依存していたため。恒常的な設定不足が根本原因
- 特定した原因:
  eslint.config.mjs の除外リストに e2e/artifacts(および playwright-report / test-results)
  が含まれていないこと。lintの対象範囲設定の不足
- 切り出したタスク: progress.txt タスク1-8(lint除外設定の修正)
- 解決日: 2026-09-22
- 解決内容:
  eslint.config.mjs の globalIgnores に e2e/artifacts/**、playwright-report/**、
  test-results/** を追加(コミット b75cc29)。artifacts生成済みの状態で npm run lint が
  exit 0 でパスすること、実コード(src/e2e配下)は引き続きlint対象であることを
  実装・レビュー双方で確認

## P-005: /admin がクライアント側で auth/invalid-api-key でクラッシュする
- 記録日: 2026-09-22
- 状態: 解決済み
- 発生箇所: src/lib/firebase-config.ts(Phase 1のタスク1-2/1-4由来の潜在バグ。タスク2-1のE2E 6件失敗として顕在化)
- 問題内容:
  想定した動き: /admin がブラウザで表示され、ログイン/アクセス拒否/管理画面の3分岐が動く
  実際の動き: クライアント側レンダリング時に getAuth() が auth/invalid-api-key を投げ、
  UIが一切描画される前にページ全体がクラッシュ。admin-auth.spec.ts が6件(3シナリオ×2プロジェクト)失敗
- 再現手順:
  1. NEXT_PUBLIC_USE_EMULATOR=true で npm run e2e を実行
  2. admin-auth.spec.ts の全シナリオが同一原因で失敗
- 原因調査:
  - firebase-config.ts の関数群が env: NodeJS.ProcessEnv = process.env を引数に取り、
    本体で env.NEXT_PUBLIC_X と間接参照していた
  - Next.js/Turbopack はクライアントバンドルへ「リテラルな process.env.NEXT_PUBLIC_X」
    のみをインライン展開する。エイリアス経由(env.NEXT_PUBLIC_X)は静的解析で見えず
    undefined になる
  - 結果、ブラウザ側で全 NEXT_PUBLIC_* が undefined となり getAuth() が例外
  - Phase 1ではクライアントからこの初期化を通る画面が無かったため潜在化していた
- 特定した原因:
  クライアント向けFirebase設定の環境変数を間接参照していたため、Next.jsの静的置換が
  効かずクライアントバンドルで値が欠落したこと
- 切り出したタスク: タスク2-1の範囲内で修正(2-1の完了条件E2Eに必須のため)
- 解決日: 2026-09-22
- 解決内容:
  firebase-config.ts を、リテラルな process.env.NEXT_PUBLIC_X を直接書く readEnv()
  ヘルパー方式に変更(呼び出しごとに評価。テストのprocess.env変更も反映)。
  Auth Emulatorモード用に demo API key フォールバックも追加。npm run e2e 8件全通過で
  解決確認。検証はタスク2-1のレビュー(daychi-review)に含めて実施。
  【今後の注意】クライアント側で NEXT_PUBLIC_* を読む場合は必ずリテラル参照にすること
  (2-2以降で新たな env 依存のクライアント設定を追加する場合に留意)

## P-017: Gemini無料枠の1日上限(20回)に達すると分かりにくいエラーで止まり、リトライで回数を浪費する
- 記録日: 2026-09-23
- 状態: 解決済み
- 発生箇所: src/lib/ai-extraction/gemini-adapter.ts / src/app/admin/import/page.tsx(4-3dの実API検証・追加調査で発覚)
- 問題内容:
  想定した動き: 利用上限に当たった時、待てば回復する制限なら待って再試行し、その日はもう使えない制限なら
                すぐ止めて管理者に分かる言葉で伝える
  実際の動き: 429はすべて1秒→2秒→4秒の待機で再試行し、失敗すると「Gemini APIがエラーを返しました(status: 429)」
              とだけ表示される。1日の上限でも再試行して回数を浪費する
- 再現手順:
  1. 同じ日に gemini-3.6-flash を20回呼んだ後、取り込みを実行
  2. 429(RESOURCE_EXHAUSTED)で失敗し、分かりにくいメッセージが出る
- 原因調査(実APIで確認):
  - 429の応答本文 error.details に以下が含まれる:
    - google.rpc.QuotaFailure: quotaId "GenerateRequestsPerDayPerProjectPerModel-FreeTier", quotaValue "20"
      (無料枠は1プロジェクト・1モデルあたり1日20リクエスト)
    - google.rpc.RetryInfo: retryDelay "37s"(1日上限でも短い待機時間が返るため、そのまま信用すると無駄に再試行する)
  - 4-3dレビューで6回中2回失敗した429、および今回の3連続429はこの1日上限/短時間の制限によるもの
  - 1日上限は太平洋時間0時(日本時間16時ごろ)にリセットされる(Googleのドキュメントの説明による)
- 特定した原因:

## P-027: Instagram URLを空欄にして保存した後、編集フォームを開き直すと前の値が表示されることがある
- 記録日: 2026-09-28
- 状態: 解決済み(2026-09-28、タスク6-1d)
- 発生箇所: 管理画面 店舗(/admin/shops)の編集フォーム。e2e/shop-instagram-link.spec.ts:131
  (6-1bレビューのフルE2E 5回中1回で発生。6-1bの変更とは無関係=src差分なし・ピンクリックなし)
- 問題内容:
  想定した動き: Instagram URLを空欄にして保存(「店舗を更新しました」表示)→編集を開き直すと空欄
  実際の動き: 開き直した編集フォームに保存前の値(https://www.instagram.com/daychi_coffee_e2e/)が表示される
- 再現手順: npm run e2e を繰り返す(観測5回中1回、desktop/mobile問わず)
- 原因調査(タスク6-1d、2026-09-28):
  1. データフロー: 「更新」ボタン押下 → handleEditSubmit が `await updateShop(...)` (Firestore書き込み完了)
     → `setEditingId(null)` (編集行が「編集」ボタン表示の通常行に戻る) → `showSuccess(...)`
     → `await reload()` (listShops() を呼び直し setShops で一覧stateを更新)。
     編集ボタン押下時は startEdit(shop) が、その時点でレンダリングされている `shops` state配列の
     要素(=画面の.map内でクロージャに捕まっているshopオブジェクト)から editForm を初期化する
     (src/app/admin/shops/page.tsx の startEdit / `shops.map((shop) => ...)` / `onClick={() => startEdit(shop)}`)。
  2. 問題箇所の特定: handleEditSubmit は `setEditingId(null)` を `await reload()` より先に実行していた。
     これにより「Firestoreへの書き込みは完了しているが、一覧stateはまだ更新前(reload未完了)」という
     窓が開いた状態で「編集」ボタンが再び押せてしまう。この窓の間に「編集」を押すと、startEditは
     reload前の古い`shops`配列から古いinstagramUrl(等)でeditFormを初期化してしまう。
  3. 実測による裏付け: reload()の先頭に人為的に400msの遅延を挿入し(検証専用の一時変更、検証後に削除)、
     e2e/shop-instagram-link.spec.ts の該当テストを5回連続実行したところ5/5回とも同一の失敗
     (shop-edit-instagram に空文字ではなく保存前のURLが入る)を再現した。これにより「テストの待ち合わせ
     不足」ではなく「保存完了通知(成功メッセージ)が一覧再取得の完了より先に表示され、その間に編集を
     再度開くと古いデータが使われる」というアプリ側のレースコンディションであることを確認した。
  4. 実利用者への影響: 実利用者でも、保存後に表示される「店舗を更新しました」を見てすぐ「編集」を
     再度押した場合(内容確認や連続修正のため)、Firestoreの読み取りにかかる時間だけこの窓が開くため
     起こりうる。その状態のまま何も変更せず保存すると、消したはずのInstagram URL(や他の編集直後の値)が
     復活して書き戻されてしまう。通常はFirestore読み取りが速いため頻度は低いが(観測5回中1回)、
     回線状況やEmulator/本番の負荷次第で発生しうる実利用者影響のある不具合と判断した。
- 特定した原因: handleEditSubmit(および同型のperformers/videos/visits/tagsの各admin CRUD画面の
  handleEditSubmit)が、一覧の再取得(reload)が完了する前に setEditingId(null) で編集モードを
  終了させてしまい、「編集」ボタンが再度押せる状態と、一覧stateがまだ更新前という状態が同時に
  成立する期間ができることによるレースコンディション。
- 修正: 上記5画面すべてで、handleEditSubmit内の `await reload()` を `setEditingId(null)` より前に
  実行する順序へ変更した(reloadで一覧stateが更新済みになってから編集モードを終了する)。これにより
  「編集」ボタンが再度押せる時点では必ず最新データがstateに入っている状態になり、レースコンディションの
  窓自体をなくした(固定待ち・リトライ追加ではなく、処理順序自体の修正)。
  修正ファイル: src/app/admin/shops/page.tsx, src/app/admin/performers/page.tsx,
  src/app/admin/videos/page.tsx, src/app/admin/visits/page.tsx, src/app/admin/tags/page.tsx
  (レビュー画面のReviewShopCard(src/components/admin/review/ReviewShopCard.tsx)は「編集/表示」の
  モード切替を持たず常に編集状態で、保存後もpropsのshopが変わらない限りローカルform stateを
  保存前の値に戻さない設計のため、同型のレースコンディションは存在せず対応不要と判断した)
- 検証:
  - 修正前 + 人為的な400ms遅延: 5/5失敗(上記3.のとおり再現)
  - 修正後 + 同じ400ms遅延を残したまま: 5/5成功(該当テストを個別実行)
  - 遅延を削除した最終コードで npm run e2e(フルE2E)を連続3回実行し、いずれも133 passed/15 skippedで
    失敗0
  - npm run typecheck / npm run lint / npm run test も全て緑
- 切り出したタスク: progress.txt タスク6-1d
